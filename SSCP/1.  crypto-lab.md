## CIA triad & authenticity

Cryptography protects confidentiality (nobody unauthorized reads it), integrity (nobody silently changes it), authenticity (you know who sent it) and availability (keys and systems stay usable).

**Flow:** Plain data → Encrypt → Hash → Sign → Verify

### Working principle
1. **Plain data**: Start with data that must be protected: personal data, trade secrets, payments.
2. **Encrypt**: Encryption with a secret key means only key holders can read it (confidentiality).
3. **Hash**: A hash gives a fixed-length fingerprint; any change alters it (integrity).
4. **Sign**: The sender encrypts the hash with a private key: a digital signature (authenticity, nonrepudiation).
5. **Verify**: The receiver decrypts the signature with the public key and compares hashes. Key management (generate, distribute, store, revoke) keeps everything available.

### Pros
- Covers four security goals with a few building blocks
- Mathematically verifiable, not trust-based

### Cons
- Only as strong as key management
- Needs a secure algorithm, random keys, a secure channel and a trusted party

### Where it is deployed
- Secure email, messaging, VoIP, video calls
- Cloud storage, backups, archives
- Passwords, biometrics, tokens
- Certificates, smart cards, RFID tags

<a id="sens"></a>
## Data sensitivity & protection

Sensitivity depends on privacy rules, value and business impact. Data classification assigns a level; protection then follows the level.

**Flow:** Raw data → Classify → Encrypt at rest → Mask on screen → Protect in transit

### Working principle
1. **Raw data**: Data alone may be harmless, but combined with other data it can become sensitive.
2. **Classify**: Data classification assigns a sensitivity level by who may access it and the harm if disclosed or lost.
3. **Encrypt at rest**: Disk, database and backup encryption protect stored data.
4. **Mask on screen**: Obfuscation, masking and screen filters stop shoulder surfing (people or cameras watching a PIN pad or screen).
5. **Protect in transit**: IPsec, SSL/TLS and S/MIME protect data crossing untrusted networks. Access control built on encryption also defends availability against denial of service.

### Pros
- Spends protection effort where harm is greatest
- Supports legal compliance and breach notification

### Cons
- Classification is judged case by case
- Over-classifying slows work; under-classifying exposes data

### Where it is deployed
- Banking and card data (PCI DSS)
- Hospitals: medical records (HIPAA-style rules)
- Government and defense classified data
- HTTPS websites and VPNs

<a id="entropy"></a>
## Entropy & randomness

Entropy measures unpredictability. Keys, salts and nonces need high entropy; predictable keys can be guessed even with a strong algorithm.

**Flow:** Entropy source → Quality check → Extract/combine → Random key → Use in cipher

### Working principle
1. **Entropy source**: Sources: physical noise, user input, algorithms, or quantum phenomena (QRNG).
2. **Quality check**: Evaluate quality and quantity: biased, correlated or compromised sources are weak.
3. **Extract/combine**: Extract and combine several sources to remove bias.
4. **Random key**: Output a key whose every bit is unpredictable.
5. **Use in cipher**: Higher entropy means more guesses for brute force: each added bit doubles the work.

### Pros
- Directly sets brute-force resistance
- QRNG gives physically unpredictable bits

### Cons
- Bad sources fail silently
- Hardware QRNG costs more than software generators

### Where it is deployed
- Key and password generation
- Online gaming and lotteries
- Scientific simulation
- Quantum RNG chips in phones and HSMs

<a id="hash"></a>
## Hashing & message digest

A hash function turns input of any size into a fixed-length digest. It is easy to compute, practically irreversible, and a single changed bit changes the whole digest.

**Flow:** Message → Hash H() → Digest → Send both → Receiver re-hashes → Compare

### Working principle
1. **Message**: The originator has a message of any size.
2. **Hash H()**: The message runs through the hash algorithm H.
3. **Digest**: A fixed-size digest (e.g. 256 bits) comes out; size reveals nothing about the message.
4. **Send both**: Digest is appended to the message and both are sent.
5. **Receiver re-hashes**: The receiver hashes the received message with the same algorithm.
6. **Compare**: Equal digests mean unchanged. Weakness: an attacker who changes both message and digest goes unnoticed, so digests are signed (see next modules).

### Pros
- Fast, fixed-size output
- Detects any alteration (avalanche effect)
- Used for file download checks

### Cons
- Plain hash does not stop an attacker swapping both message and digest
- Weak algorithms (MD5, SHA-1) suffer collisions

### Where it is deployed
- Software download verification
- Digital signatures, MACs
- Deduplication and fingerprinting
- Checksums for corrupted data

<a id="hashes"></a>
## Hash algorithm family

MD2/4/5, SHA-0/1/2/3, HAVAL and RIPEMD-160 differ in digest size, block size, rounds and, importantly, which are still safe.

**Flow:** MD2/4/5 → SHA-0/1 → SHA-2 → SHA-3 (Keccak) → RIPEMD/HAVAL

### Working principle
1. **MD2/4/5**: MD family (1989-1992): MD2 128-bit, MD4 three rounds, MD5 four rounds; all have published collision attacks.
2. **SHA-0/1**: SHA-0 was withdrawn for flaws; SHA-1 (1995, 160-bit) is no longer safe (birthday attack).
3. **SHA-2**: SHA-2 (2001): 224, 256, 384, 512-bit digests; blocks of 512 or 1024 bits.
4. **SHA-3 (Keccak)**: SHA-3 (NIST 2015): Keccak sponge construction, absorbs any input then squeezes output. A drop-in alternative, not a replacement; SHA-2 stays.
5. **RIPEMD/HAVAL**: HAVAL: configurable 128-256 bit. RIPEMD-160: European design, 160-bit, patent-free.

### Pros
- SHA-2/3 remain strong
- Standardized and built into every OS and browser
- SHA-3 offers a different internal design as a backup

### Cons
- Older members are broken
- Legacy systems still use them
- Attacks keep appearing, so migration is ongoing

### Where it is deployed
- SHA-256: TLS certificates, Bitcoin
- RIPEMD-160: Bitcoin addresses
- MD2: legacy PKI certificates
- MD4/MD5: legacy file sync (not for security)

<a id="sig"></a>
## Digital signature (hash + key)

A signature encrypts the hash with the sender’s private key. Anyone can check it with the public key, so the attacker cannot forge a matching digest.

**Flow:** Message → Hash → Sign with private key → Transmit → Verify with public key → Accept / reject

### Working principle
1. **Message**: Sender prepares the message.
2. **Hash**: Hash the message to a digest.
3. **Sign with private key**: Encrypt the digest with the sender’s private key to make the signature.
4. **Transmit**: Send message + signature across the network (attacker may tamper here).
5. **Verify with public key**: Receiver decrypts the signature with the public key and hashes the received message.
6. **Accept / reject**: Match = intact and from the claimed sender. Mismatch = reject.

### Pros
- Authenticity, integrity and nonrepudiation together
- Public verification, no shared secret

### Cons
- Needs PKI and trusted certificates
- Private key theft breaks everything
- Slower than plain hashing

### Where it is deployed
- Code signing and software updates
- TLS certificates
- E-contracts, e-invoicing
- Government e-ID and passports

<a id="salt"></a>
## Salting passwords

A random salt is added to each password before hashing. Identical passwords give different stored hashes and precomputed rainbow tables stop working.

**Flow:** Password → Add random salt → Hash → Store salt + hash → Login: repeat → Compare

### Working principle
1. **Password**: User chooses a password.
2. **Add random salt**: A new random salt is generated for this user.
3. **Hash**: Salt and password are concatenated and hashed.
4. **Store salt + hash**: Database stores the salt and the hash, never the plaintext.
5. **Login: repeat**: At login the typed password is combined with the stored salt and hashed again.
6. **Compare**: Equal hashes authenticate the user. A rainbow table would need entries for every salt, which is infeasible.

### Pros
- Defeats rainbow tables and dictionary reuse
- Hides duplicate passwords

### Cons
- Does not stop brute force on weak passwords
- Needs slow hashes (bcrypt, Argon2) for real strength

### Where it is deployed
- Linux /etc/shadow
- Web app user databases
- WordPress, Django, banking logins
- Password managers

<a id="caesar"></a>
## Caesar vs DES (CrypTool)

Both are symmetric ciphers. Caesar shifts letters and keeps word shapes, so frequency analysis breaks it. DES scrambles blocks so the ciphertext leaks little.

**Flow:** Plaintext → Choose key → Encrypt → Ciphertext → Attacker analyses

### Working principle
1. **Plaintext**: Plaintext: “The quick brown fox jumps over the lazy dog”.
2. **Choose key**: Key: Caesar uses a shift (1 of 25); DES uses a 56-bit key.
3. **Encrypt**: Encrypt: Caesar rotates letters; DES transforms 64-bit blocks in 16 rounds.
4. **Ciphertext**: Caesar output keeps spaces and repeats (“vjg” twice). DES output is a hex blob.
5. **Attacker analyses**: The attacker finds repeated words and letter frequencies, or just tries all 26 shifts. DES needs real key search.

### Pros
- Caesar: easy to teach
- DES: far better diffusion

### Cons
- Caesar: trivially breakable
- DES: 56-bit key is now brute-forceable; replaced by AES

### Where it is deployed
- Caesar: teaching, puzzles (ROT13)
- DES/3DES: legacy banking and ATM systems
- AES: modern successor everywhere
- CrypTool: free learning portal

<a id="qkd"></a>
## Quantum key distribution (BB84)

Alice sends photons in random bases; Bob measures in random bases. An eavesdropper Eve disturbs the photons, raising the error rate and exposing her.

**Flow:** Alice sends photons → Bob measures → Compare bases → Check errors → Distill key / abort

### Working principle
1. **Alice sends photons**: Alice encodes random bits in random bases (+ or ×) on single photons.
2. **Bob measures**: Bob measures each in a random basis; wrong basis gives a random result.
3. **Compare bases**: Over a public channel they compare bases only and keep matching positions (sifting).
4. **Check errors**: They sample the kept bits: Eve’s interception causes errors (about 25% in this model).
5. **Distill key / abort**: Below threshold (~11%): error correction and privacy amplification yield a key, then AES or one-time pad. Above: abort and retry.

### Pros
- Eavesdropping is detectable (no-cloning theorem)
- Information-theoretic key security

### Cons
- Low key rate, high cost, limited distance
- Needs special hardware, noise-sensitive

### Where it is deployed
- Finance: bank-to-bank links (e.g. Geneva, Vienna trials)
- Defense: command links, satellite QKD (China Micius)
- Healthcare: protected records
- Science: secure research data sharing

<a id="qproto"></a>
## Quantum protocols: QSDC, QDS, QRNG, QSS

Beyond QKD, quantum physics supports direct secret messaging, signatures, true random numbers and shared secrets.

**Flow:** QSDC → QDS → QRNG → QSS → Quantum tech stack

### Working principle
1. **QSDC**: QSDC sends the secret message directly with entanglement and no-cloning, with no prior key (military, diplomatic).
2. **QDS**: QDS signs with a quantum state that many recipients can verify; prevents forgery and repudiation (e-voting, contracts).
3. **QRNG**: QRNG derives random bits from photon detection or vacuum fluctuations (cryptography, gaming, simulation).
4. **QSS**: QSS lets a dealer split a secret so only a qualified subset can rebuild it (distributed computing, cloud storage).
5. **Quantum tech stack**: Underneath: quantum communication, computation, measurement and error correction.

### Pros
- Security rooted in physics
- Enables post-quantum-era designs

### Cons
- Mostly experimental or niche
- Needs error correction against decoherence

### Where it is deployed
- QRNG chips in smartphones
- Diplomatic and military links
- Quantum networks (EU, US, China)
- Cloud-secret sharing research

<a id="law"></a>
## Dual-use cryptography & law

Cryptography serves civilians and militaries, so countries regulate it, yet other laws demand it for protecting data.

**Flow:** Algorithm → Export controls → Mandatory encryption → Standards (PCI DSS) → Product launch

### Working principle
1. **Algorithm**: Crypto is dual use: the same algorithm protects shoppers and soldiers.
2. **Export controls**: Many countries treat it like weapons: restricted distribution and export.
3. **Mandatory encryption**: Yet privacy and data laws require sensitive data to be protected.
4. **Standards (PCI DSS)**: Standards such as PCI DSS require cardholder data to be unreadable and need-to-know.
5. **Product launch**: Companies selling worldwide must navigate conflicting rules; some governments see encrypted personal messaging as suspect.

### Pros
- Keeps strong crypto from adversaries
- Forces baseline data protection

### Cons
- Conflicting rules across countries
- Compliance cost and legal uncertainty

### Where it is deployed
- Secure chat apps launching internationally
- Payment processors (PCI DSS)
- Defense exports
- Cloud providers in multiple regions

| **BB84** | Bennett-Brassard 1984 | First QKD protocol |
| **QSDC** | Quantum Secure Direct Communication | Sends message without a key |
| **QDS** | Quantum Digital Signatures | Quantum-verifiable signatures |
| **QRNG** | Quantum Random Number Generation | Random bits from quantum sources |
