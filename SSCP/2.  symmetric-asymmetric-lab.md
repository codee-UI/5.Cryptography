## Symmetric encryption (same key)

One shared secret key encrypts and decrypts; decryption is the mirror image of encryption. Fast, but the key must reach both parties safely and the number of keys explodes as users grow.

**Flow:** Plaintext → Encrypt (key K) → Ciphertext → Decrypt (same K) → Plaintext

### Working principle
1. **Plaintext**: Alice and Bob agree on a key K. It must travel out-of-band (courier, phone, fax), never on the same channel as the data, or a machine-in-the-middle (MITM) copies it.
2. **Encrypt (key K)**: Alice encrypts the plaintext with K.
3. **Ciphertext**: The ciphertext crosses the untrusted network; without K it is unreadable.
4. **Decrypt (same K)**: Bob decrypts with the same K, running the steps in reverse.
5. **Plaintext**: Limits: anyone holding K can also change the message, so origin is unprovable (weak authenticity); every pair or group needs its own key: n(n−1)/2 keys, so 1,000 staff need 499,500.

### Pros
- Very fast; ideal for bulk data
- Simple and hardware-friendly
- Strong with long keys (AES-256)

### Cons
- Key distribution is hard
- Key count grows as n(n−1)/2
- No nonrepudiation: shared key means anyone could have written it

### Where it is deployed
- Disk and backup encryption (BitLocker, FileVault)
- IPsec VPNs, TLS data channel
- Wi-Fi (WPA2/3 with AES)
- Military radio links, card payment PIN blocks

<a id="stream"></a>
## Stream ciphers (keystream XOR)

A key seeds a keystream generator; each plaintext bit or byte is XORed with the matching keystream bit as it flows. Quick and low-latency, so it suits voice and hardware.

**Flow:** Key → Keystream generator → Keystream → XOR with plaintext → Ciphertext

### Working principle
1. **Key**: A fixed-length key (e.g. 10110111) is the secret.
2. **Keystream generator**: The keystream generator expands it into a pseudorandom bit stream. Sender and receiver must get identical streams, so it cannot be truly random.
3. **Keystream**: Keystream bits are produced continuously, one symbol at a time.
4. **XOR with plaintext**: Each plaintext bit is XORed with a keystream bit (same bits → 0, different → 1).
5. **Ciphertext**: Ciphertext is sent. Receiver XORs again with the same keystream to recover plaintext. Any generator eventually repeats, so messages must be shorter than the repeat interval.

### Pros
- Encrypts symbol by symbol with minimal delay
- Easy to build in hardware
- Errors do not spread to other blocks

### Cons
- Reusing a keystream is catastrophic
- Keystream repeat limits message length
- RC4 is banned by NIST for federal sensitive data

### Where it is deployed
- Voice calls (GSM A5, VoIP)
- RC4 in WEP and early WPA
- Bluetooth E0, ChaCha20 in modern TLS and Signal
- Satellite and military link encryptors

<a id="block"></a>
## Block ciphers, modes & IV

A block cipher encrypts a whole fixed-size block per operation (AES: 128 bits). Modes decide how blocks combine: ECB, CBC for no-latency-concern data; CFB, OFB, CTR to imitate a stream cipher. An initialization vector (IV) adds variance.

**Flow:** Split into blocks → Pick mode → Apply IV / chaining → Encrypt blocks → Ciphertext blocks

### Working principle
1. **Split into blocks**: Long messages are cut into blocks (padding the last one).
2. **Pick mode**: ECB and CBC suit data where latency is not a concern; CFB, OFB and CTR work like stream ciphers when latency matters.
3. **Apply IV / chaining**: The IV (non-secret nonce, a number used once) starts the chain and synchronizes both ends.
4. **Encrypt blocks**: ECB encrypts each block alone (equal blocks give equal output); CBC XORs each plaintext block with the previous ciphertext block; CTR XORs with the encrypted counter.
5. **Ciphertext blocks**: Rounds of substitution and transposition scramble each block. Try the modes below and watch repeated blocks.

### Pros
- More robust than most stream designs
- Many modes fit many needs
- CTR/GCM allow parallelism

### Cons
- Latency: must wait for a full block
- ECB leaks patterns
- IV reuse breaks security

### Where it is deployed
- AES-CBC/GCM in TLS and disk encryption
- Database field encryption
- CTR in Wi-Fi CCMP
- Secure file storage in cloud services

<a id="symalgos"></a>
## Symmetric algorithm catalogue

DES, 3DES, AES (Rijndael), IDEA, CAST, SAFER, Blowfish, Twofish, RC4, RC5, MARS and Serpent differ in key size, block size, rounds and survival.

**Flow:** DES / 3DES → AES (Rijndael) → IDEA / CAST / SAFER → Blowfish / Twofish → RC4 / RC5

### Working principle
1. **DES / 3DES**: DES: 64-bit key with every 8th bit parity, so 56 effective bits. Double DES fell; Triple DES (strength ~2^112 with two keys) soon fell too, so all DES variants were abandoned.
2. **AES (Rijndael)**: Rijndael supports 128/192/256-bit blocks and keys; AES fixes the block at 128 bits with 10, 12 or 14 rounds for 128/192/256-bit keys.
3. **IDEA / CAST / SAFER**: IDEA (Lai & Massey, 1991): 128-bit key, 64-bit blocks, 8 rounds. CAST-128 (Adams & Tavares, 1996): 40-128 bit keys, 12-16 rounds; CAST-256: 48 rounds. SAFER (Massey): patent-free, a variant in Bluetooth.
4. **Blowfish / Twofish**: Blowfish (Schneier): keys 32-448 bits, 64-bit blocks, key-built S-boxes, fast but slow to rekey. Twofish: AES finalist, 128-bit blocks, 16 rounds.
5. **RC4 / RC5**: RC4 (Rivest, 1987): stream cipher, 8-2048-bit key. RC5: key up to 2040 bits, up to 255 rounds, 16/32/64-bit words, four modes (RC5, CBC, CBC-Pad, CTS).

### Pros
- AES, Twofish: fast and trusted
- Wide choice, some patent-free
- Blowfish/Twofish free to use

### Cons
- DES/3DES retired
- RC4 weak in practice and banned by NIST
- Blowfish unsuitable where keys change often or on smart cards

### Where it is deployed
- AES: governments, banks, Wi-Fi, HTTPS
- 3DES: legacy ATMs (being phased out)
- Blowfish: password hashing (bcrypt)
- SAFER variant: Bluetooth

<a id="ccmp"></a>
## AES-CCMP: Wi-Fi security (WPA2/WPA3)

CCMP combines AES in counter mode (confidentiality) with CBC-MAC (integrity and origin). It replaced WEP/RC4 and TKIP and is mandatory in 802.11i Robust Security Networks.

**Flow:** Frame + header → RSN negotiation → MIC (CBC-MAC) → CTR encrypt → Receiver verifies

### Working principle
1. **Frame + header**: A wireless packet has a MAC header and payload (MPDU).
2. **RSN negotiation**: Robust Security Network (RSN) negotiates algorithms between access point and client; AES-CCMP is mandatory (TKIP allowed for legacy).
3. **MIC (CBC-MAC)**: CBC-MAC with a 128-bit AES key computes a message integrity code (MIC) over the payload and parts of the header: data-origin authentication and integrity.
4. **CTR encrypt**: CTR mode encrypts the payload with a 128-bit key and a 48-bit packet number (IV), which minimizes replay attack exposure.
5. **Receiver verifies**: Receiver decrypts, recomputes the MIC and checks the packet number: tampered or replayed frames are dropped. Defined in RFC 3610 and IEEE 802.11i.

### Pros
- Confidentiality plus integrity in one design
- Protects header parts, not only payload
- Replay-resistant

### Cons
- Needs AES hardware for speed on old gear
- Only as good as the Wi-Fi passphrase
- Not a fix for weak endpoint security

### Where it is deployed
- Home and enterprise Wi-Fi (WPA2/3)
- Military and hospital wireless LANs
- Public hotspots with WPA3
- Industrial wireless sensors

<a id="asym"></a>
## Asymmetric encryption (public / private key)

Two mathematically linked keys: the public key is shared, the private key stays secret. Public encrypts, private decrypts (confidentiality); private signs, public verifies (proof of origin, nonrepudiation).

**Flow:** Recipient makes key pair → Publish public key → Sender encrypts with public → Ciphertext travels → Recipient decrypts with private

### Working principle
1. **Recipient makes key pair**: The recipient generates a key pair (usually by software or PKI, not by hand).
2. **Publish public key**: The public key is published (website, key server, certificate); the private key never leaves the owner.
3. **Sender encrypts with public**: The sender encrypts with the recipient’s public key: only the matching private key can open it.
4. **Ciphertext travels**: The ciphertext crosses the untrusted channel with no prior secret exchange.
5. **Recipient decrypts with private**: Only the private-key holder decrypts: confidentiality. Reverse use: encrypt with the sender’s private key and anyone can decrypt with the public key, proving origin.

### Pros
- No prior key exchange
- Enables signatures and nonrepudiation
- Supports confidentiality, integrity, authenticity, privacy and safety goals

### Cons
- Many times slower than symmetric
- Impractical for messages above roughly 64 KB
- Needs PKI to trust public keys

### Where it is deployed
- HTTPS key exchange and certificates
- PGP / S/MIME email
- Code signing and software updates
- Government e-passports and e-ID

<a id="trapdoor"></a>
## Trapdoor functions: factoring & discrete log

Easy forward, infeasible backward. RSA relies on factoring the product of two large primes; ECC, ElGamal and Diffie-Hellman rely on the discrete logarithm problem.

**Flow:** Choose secret numbers → Compute forward (easy) → Publish result → Attacker reverses (hard) → Owner uses trapdoor

### Working principle
1. **Choose secret numbers**: Prime factoring: pick two primes hundreds of digits long. Discrete log: pick secret exponent n.
2. **Compute forward (easy)**: Forward: multiply the primes, or compute x = c·b^n by repeated multiplication. Fast.
3. **Publish result**: The product / x becomes (part of) the public key.
4. **Attacker reverses (hard)**: Backward: factor the product, or solve for n. Millions of operations even for small numbers, tens of thousands of CPU-years for real sizes (botnets and GPUs parallelize the attack).
5. **Owner uses trapdoor**: The key owner knows the secret that makes reversal easy: the trapdoor. Only RSA uses factoring; ECC, ElGamal, DH use discrete logs.

### Pros
- Security from a hard math problem
- Public key can be derived from private easily

### Cons
- Quantum computers (Shor) threaten both problems
- Large keys needed (RSA 2048+, ECC 256)

### Where it is deployed
- RSA: TLS certificates, signatures
- ECC: Bitcoin, iMessage, TLS 1.3
- DH: VPN and TLS key agreement
- Post-quantum migration in banks and defense

<a id="dh"></a>
## Diffie-Hellman session key on demand

Two parties compute the same symmetric session key without ever sending it, using public numbers and private exponents.

**Flow:** Agree p and g → Pick private a / b → Exchange public A / B → Compute shared secret → Use as symmetric key

### Working principle
1. **Agree p and g**: Public parameters p (prime) and g are known to everyone.
2. **Pick private a / b**: Alice picks secret a, Bob picks secret b.
3. **Exchange public A / B**: Alice sends A = g^a mod p; Bob sends B = g^b mod p. Eve sees both.
4. **Compute shared secret**: Alice computes B^a mod p, Bob computes A^b mod p: identical value.
5. **Use as symmetric key**: That value becomes the symmetric session key for fast bulk encryption. Eve would need the discrete log.

### Pros
- Solves key distribution
- Forward secrecy with ephemeral keys

### Cons
- Unauthenticated DH allows MITM; needs signatures or certificates
- Weak parameters are breakable

### Where it is deployed
- TLS, SSH, IPsec/IKE
- Signal and WhatsApp
- VPN gateways
- Military link key agreement

<a id="pki"></a>
## PKI, certificates & certificate authorities

A certificate binds an identity to a public key, signed by a certificate authority (CA). PKI is the system of CAs, servers, standards and software that creates, distributes and validates them.

**Flow:** Generate key pair → Send request to CA → CA verifies identity → CA issues certificate → Others verify & use

### Working principle
1. **Generate key pair**: The key pair is generated on a device or by an enterprise key server; the private key stays there.
2. **Send request to CA**: The requester sends the public key, identity details and algorithm info to the CA.
3. **CA verifies identity**: The CA checks the identity. It registers the public key and information in its vault but never the private key.
4. **CA issues certificate**: The CA signs and returns a digital certificate that ties identity to public key.
5. **Others verify & use**: Anyone who trusts the CA validates the certificate and can encrypt to the owner or verify their signatures. Public CAs are private companies; organizations can run their own private CAs.

### Pros
- Scales trust to billions of users
- Standardized and built into OS and browsers

### Cons
- Trust depends on CAs (compromised CAs are dangerous)
- Revocation and expiry management is hard

### Where it is deployed
- HTTPS websites
- Corporate VPN and smart cards
- Government e-ID, military CAC cards
- Code signing, IoT device identity

<a id="compare"></a>
## Symmetric vs asymmetric & hybrid use

Asymmetric solves distribution and adds signatures but is slow; symmetric is fast. Real systems combine them: asymmetric to agree on a key, symmetric to encrypt data.

**Flow:** Client hello → Verify certificate → Asymmetric key exchange → Session key shared → AES bulk data

### Working principle
1. **Client hello**: Client contacts the server.
2. **Verify certificate**: Server presents a certificate; client validates it through PKI.
3. **Asymmetric key exchange**: Client encrypts a session key with the server’s public key (or both use Diffie-Hellman).
4. **Session key shared**: Server decrypts with its private key: both hold the same session key. Availability benefits too, since encryption-backed access control resists denial-of-service and disruption.
5. **AES bulk data**: Bulk data flows with fast symmetric encryption (AES).

### Pros
- Speed of symmetric plus convenience of asymmetric
- Provides confidentiality, integrity, authenticity, nonrepudiation

### Cons
- Complexity: more moving parts to configure
- Weak link in either half undermines the whole

### Where it is deployed
- HTTPS/TLS everywhere
- Banking and card payments
- Secure messaging
- Defense and satellite command links

## Glossary

| Term | Full form | Meaning |
|---|---|---|
| **MITM** | Machine-in-the-Middle (man-in-the-middle) | Attacker intercepting a channel |
| **Out-of-band** | Key sent over a different channel | Courier, phone or fax |
| **XOR** | Exclusive OR | Bit operation: equal bits give 0 |
| **IV** | Initialization Vector | Non-secret nonce that starts encryption |
| **Nonce** | Number used once | Unique value, often the IV |
| **DES** | Data Encryption Standard | 56-bit effective key, retired |
| **2DES / 3DES** | Double / Triple DES | DES applied repeatedly, retired |
| **AES** | Advanced Encryption Standard | 128-bit block, 128/192/256-bit key |
| **IDEA** | International Data Encryption Algorithm | 128-bit key, 64-bit block |
| **CAST** | Carlisle Adams and Stafford Tavares | Feistel cipher family |
| **SAFER** | Secure And Fast Encryption Routine | Patent-free block cipher |
| **RC4/5/6** | Rivest Cipher 4, 5, 6 | Ron Rivest’s ciphers (RC4 stream) |
| **MARS / Serpent** | AES finalist ciphers | Alternative block ciphers |
| **Feistel** | Feistel network | Cipher design splitting a block in halves |
| **S-box** | Substitution box | Lookup table that scrambles bits |
| **LFSR** | Linear Feedback Shift Register | Simple keystream generator |
| **ECB** | Electronic Code Book | Each block encrypted independently |
| **CBC** | Cipher Block Chaining | Block XORed with previous ciphertext |
| **CFB** | Cipher Feedback | Stream mode from a block cipher |
| **OFB** | Output Feedback | Stream mode, keystream independent of data |
| **CTR** | Counter | Stream mode using an incrementing counter |
| **CTS** | Ciphertext Stealing | Same-length ciphertext for any input |
| **WEP** | Wired Equivalent Privacy | Old Wi-Fi security on RC4, broken |
| **WPA / WPA2 / WPA3** | Wi-Fi Protected Access | Wi-Fi security standards |
| **CCMP** | Counter Mode with CBC-MAC Protocol | AES-based Wi-Fi protection |
| **TKIP** | Temporal Key Integrity Protocol | Legacy Wi-Fi protocol |
| **RSN** | Robust Security Network | 802.11i network negotiating algorithms |
| **MIC** | Message Integrity Code | Tag proving integrity and origin |
| **MPDU** | MAC Protocol Data Unit | Wi-Fi frame payload unit |
| **IEEE / IETF** | Institute of Electrical and Electronics Engineers / Internet Engineering Task Force | Standards bodies |
| **FIPS** | Federal Information Processing Standard | US government standard (FIPS 197 = AES) |
| **RFC** | Request for Comments | Internet standards document |
| **NIST** | National Institute of Standards and Technology | US standards body |
| **PKI** | Public-Key Infrastructure | Trust system for certificates |
| **CA** | Certificate Authority | Issues and signs certificates |
| **RSA** | Rivest-Shamir-Adleman | Prime-factoring public-key algorithm |
| **ECC** | Elliptic Curve Cryptography | Discrete-log on curves |
| **DH** | Diffie-Hellman(-Merkle) | Key agreement protocol |
| **ElGamal** | Taher ElGamal’s algorithm | Discrete-log encryption |
| **DDoS** | Distributed Denial of Service | Overload attack on availability |
| **CPU / GPU** | Central / Graphics Processing Unit | Hardware used in parallel attacks |
| **Trapdoor function** | Easy forward, hard backward | Basis of public-key crypto |
| **IPsec / TLS** | Internet Protocol Security / Transport Layer Security | Network encryption protocols |
