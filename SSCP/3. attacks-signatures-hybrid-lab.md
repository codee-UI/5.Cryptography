<a id="nonrep"></a>
## Nonrepudiation: signatures vs HMAC vs audit trail

Nonrepudiation means no party can deny taking part in a transaction. It needs verifiable proof of origin, identity and content. Digital signatures with certificates provide it; HMACs and audit trails help but do not.

**Flow:** Transaction → Evidence created → Dispute: “I never sent it” → Evidence checked → Verdict

### Working principle
1. **Transaction**: Two parties exchange a message, contract or payment with no physical signatures or witnesses.
2. **Evidence created**: Evidence is produced: a digital signature (private key), an HMAC (shared key) or an audit-trail entry (time, source, destination, content).
3. **Dispute: “I never sent it”**: One side repudiates, the opposite of nonrepudiation. Deniability lets a party disown it without any proof; accountability makes them answer for it with evidence.
4. **Evidence checked**: Only a private key held by one person can have produced a signature, so the certificate binds the act to that identity. A shared HMAC key could come from either side, and logs only trace origin.
5. **Verdict**: Signature: sender cannot deny, receiver cannot claim a forgery. HMAC: integrity and origin, no nonrepudiation. Audit trail: chronology and tracing, no nonrepudiation.

### Pros
- Prevents disputes, fraud and tampering
- Legally admissible proof of origin, identity, content
- Builds trust in e-commerce, banking, healthcare, government

### Cons
- Depends on private-key secrecy
- Needs certificates and a trusted CA
- Strength limited by the algorithm and key length

### Where it is deployed
- E-contracts and e-invoicing
- Banking and payment authorisation
- Healthcare e-prescriptions and records
- Government filings, defense order authentication

<a id="hmac"></a>
## HMAC (hash-based message authentication code)

A secret key and a hash function produce a fixed-length tag attached to the message. It proves integrity and that the sender knew the shared key, but not who of the two key holders sent it.

**Flow:** Shared secret key → Compute HMAC tag → Send message + tag → Receiver recomputes → Compare tags

### Working principle
1. **Shared secret key**: Sender and receiver share a secret key (SHA-256 or another secure hash underneath).
2. **Compute HMAC tag**: The sender hashes message and key together to a fixed-length tag.
3. **Send message + tag**: Message and tag travel together over the untrusted channel.
4. **Receiver recomputes**: The receiver computes the HMAC of the received message with their copy of the key.
5. **Compare tags**: Equal tags mean untampered and sent by a key holder. Because both parties hold the key, either could have made the tag: no nonrepudiation.

### Pros
- Fast, symmetric-key speed
- Integrity and origin authentication
- Simple to implement

### Cons
- No nonrepudiation (shared key)
- Key distribution problem remains
- MD5-based HMACs are discouraged

### Where it is deployed
- TLS record protection, IPsec ESP/AH
- API request signing (cloud services)
- JWT tokens (HS256)
- Military link authentication, SecurID-style tokens

<a id="audit"></a>
## Audit trails

An audit trail records events of a transaction: time, date, source, destination and content. It cannot prove who is responsible, but it traces origins and establishes chronology for investigations.

**Flow:** Event occurs → Log entry written → Stored by parties → Dispute / investigation → Chronology rebuilt

### Working principle
1. **Event occurs**: A message is sent, relayed, received or validated.
2. **Log entry written**: Each system logs time, date, source, destination and content reference.
3. **Stored by parties**: Sender, receiver, intermediary and CA may each keep copies.
4. **Dispute / investigation**: In a dispute the logs are collected as evidence.
5. **Chronology rebuilt**: Investigators order the events to reconstruct sequence and validity. Logs alone are not nonrepudiation since they can be incomplete or altered.

### Pros
- Supports forensics and compliance
- Multiple independent copies add confidence

### Cons
- Not proof of identity
- Logs can be altered unless protected
- Storage and privacy overhead

### Where it is deployed
- SIEM and security operations centres
- Bank transaction records
- Hospital record-access logs
- Defense command-and-control logging

<a id="dsig"></a>
## Digital signatures & message encryption (S/MIME)

A signature is the sender’s private-key encryption of the message digest: it gives authentication, nonrepudiation and integrity but not secrecy. Encryption gives confidentiality. They are independent and are often combined.

**Flow:** Alice: message → Hash H → Alice’s digest → Encrypt (E) with private key → Send message + signature → Bob: hash H and decrypt (D) with public key → Digests equal: Verified

### Working principle
1. **Alice: message**: Alice (sender) writes the message.
2. **Hash H → Alice’s digest**: The hash function H makes Alice’s digest, proving integrity.
3. **Encrypt (E) with private key**: E encrypts the digest with Alice’s private key: the digital signature (proves who sent it).
4. **Send message + signature**: The message and signature travel to Bob; the message itself is not confidential.
5. **Bob: hash H and decrypt (D) with public key**: Bob hashes the message himself (Bob’s digest) and decrypts the signature with Alice’s public key (Alice’s digest).
6. **Digests equal: Verified**: If both digests match: Verified. Using S/MIME on SMTP email adds encryption, since plain SMTP can be read by anyone en route.

### Pros
- Authentication, nonrepudiation, integrity together
- Legally binding in the US, EU and many countries
- Combines freely with encryption

### Cons
- Signature alone does not hide content
- Needs certificates/PKI
- Order matters: sign-then-encrypt vs encrypt-then-sign

### Where it is deployed
- Signed and encrypted email (S/MIME)
- Software updates and code signing
- Contracts and e-government
- Blockchain smart contracts

<a id="aesrsa"></a>
## AES vs RSA

AES is a fast symmetric cipher chosen by NIST to replace DES and 3DES; RSA (1978) is the most widely used public-key algorithm, for keys and signatures.

**Flow:** 1997 NIST call → Finalists compete → Rijndael wins → AES standard → RSA complements AES

### Working principle
1. **1997 NIST call**: NIST asks for a successor to DES/3DES: at least as strong, larger block, faster in software, royalty-free, flexible.
2. **Finalists compete**: Finalists: Rijndael, Serpent (Ross Anderson), MARS (IBM), RC6 (Rivest) and Twofish (Schneier).
3. **Rijndael wins**: Rijndael by Joan Daemen and Vincent Rijmen of Belgium wins.
4. **AES standard**: AES: 128-bit block, 128/192/256-bit keys; no practical attack other than brute force (AES-256 brute force would take a billion years or more).
5. **RSA complements AES**: RSA (Rivest, Shamir, Adleman, MIT 1978) relies on factoring primes; keys of 2048 bits are default (OpenSSL, Windows), CA/Browser Forum minimum 3072 in some policies. RSA protects small items (keys, signatures); AES protects the bulk data.

### Pros
- AES: fast, no practical attacks, royalty-free
- RSA: key exchange and signatures without shared secret

### Cons
- AES: shared key must be distributed
- RSA: slow, large keys, vulnerable to factoring advances, quantum, side channels, bad implementation

### Where it is deployed
- AES: TLS, SSH, IPsec, WPA2, BitLocker, government secrets
- RSA: SSL/TLS handshakes, PGP, S/MIME, PKI certificates
- Banking, military and healthcare systems use both

<a id="hybrid"></a>
## Hybrid encryption, digital envelope & session keys

Symmetric encryption protects the large message, asymmetric encryption protects the small symmetric key. The pair travels as a digital envelope, and the one-use key is a session key.

**Flow:** Make session key → Encrypt message (AES) → Encrypt key (RSA public) → Send digital envelope → Recipient opens, key discarded

### Working principle
1. **Make session key**: The sender generates a random symmetric session key used for one session only.
2. **Encrypt message (AES)**: The large message is encrypted quickly with the symmetric algorithm.
3. **Encrypt key (RSA public)**: The small key (128 to 4096 bits) is encrypted with the receiver’s public key.
4. **Send digital envelope**: Encrypted message and encrypted key are sent together: a digital envelope.
5. **Recipient opens, key discarded**: The receiver’s private key recovers the session key, which decrypts the message; the session key is then discarded. Reversing the asymmetric use (private key) adds proof of origin.

### Pros
- Fast bulk encryption plus easy key exchange
- Fresh key every session limits damage of a leak

### Cons
- Two algorithms to get right
- Public-key trust still needs PKI

### Where it is deployed
- HTTPS/TLS, SSH
- PGP and S/MIME email
- Hospital imaging transfer
- Satellite and military data links

<a id="iv"></a>
## Cryptanalysis & the initialization vector (WEP failure)

Cryptanalysis studies weaknesses in ciphers; it is a method, not a motive (pen testers, law enforcement, criminals). Predictability helps attackers, so a random IV makes similar messages encrypt differently.

**Flow:** Collect similar ciphertexts → Look for patterns → Exploit weak IV → Recover key/plaintext → Fix: random, long IV

### Working principle
1. **Collect similar ciphertexts**: Organizations send many similar-format messages under one key.
2. **Look for patterns**: A cryptanalyst compares them for similarities and differences.
3. **Exploit weak IV**: Without a random IV, identical plaintext gives identical ciphertext; WEP’s RC4 IV was too short, so IVs repeated.
4. **Recover key/plaintext**: Repeated keystreams let attackers XOR two ciphertexts and cancel the key; WEP traffic was compromised.
5. **Fix: random, long IV**: A long random IV added to each message makes ciphertext substantially different even under the same key.

### Pros
- Cryptanalysis finds weaknesses before criminals do
- IVs are cheap and effective

### Cons
- Short or reused IVs destroy security
- Predictable keys and patterns remain a risk

### Where it is deployed
- Penetration testing and red teams
- Standards evaluation (NIST competitions)
- Wi-Fi upgrade from WEP to WPA2/3
- Intelligence and counterintelligence

<a id="attacks"></a>
## Cryptanalytic attack catalogue

Attacks differ by what the attacker knows or controls: ciphertext only, known or chosen plaintext, chosen ciphertext, or the implementation and people around the algorithm.

**Flow:** Observe → Gather samples → Choose attack → Recover key/data → Defender counter

### Working principle
1. **Observe**: Attacker identifies the target cryptosystem and what access they have.
2. **Gather samples**: They gather ciphertext, plaintext pairs, hashes or timing data.
3. **Choose attack**: They choose the attack matching their access (select one below to see its position).
4. **Recover key/data**: They recover the key, plaintext or a forged message.
5. **Defender counter**: Defenders raise the work factor, add padding, salts, nonces, constant-time code and training.

### Pros
- Each attack suggests a specific defense
- Knowing them guides algorithm choice

### Cons
- New attacks keep appearing
- Implementation attacks bypass strong math

### Where it is deployed
- Security audits
- Algorithm competitions (AES, SHA-3)
- National security cryptanalysis
- Vendor product testing

<a id="pwd"></a>
## Password attacks, rainbow tables & clipping levels

Systems store password hashes. Brute force, dictionary and rainbow-table attacks try to match them; salting defeats tables and clipping levels lock accounts after too many online failures.

**Flow:** Stolen hash file → Pick attack → Hash guesses → Match found? → Defense: salt + lockout

### Working principle
1. **Stolen hash file**: Systems store only password hashes (e.g. a SAM file).
2. **Pick attack**: Brute force tries every combination; dictionary tries natural words and variants such as 0 for o, 3 for e, @ for a; rainbow tables look up precomputed hashes.
3. **Hash guesses**: Each guess is hashed and compared with the stored hash.
4. **Match found?**: A match reveals the password. Offline attacks on a copied file have no lockout.
5. **Defense: salt + lockout**: Salt breaks table lookups; a clipping level (allowed wrong tries) stops online brute force; longer, complex passwords raise the work factor.

### Pros
- Hashing never stores plaintext
- Clipping levels stop online guessing
- Salt kills precomputed tables

### Cons
- Weak words fall quickly
- Offline attacks ignore lockouts
- Lockouts can be abused for denial of service

### Where it is deployed
- Operating system logins
- Web application user stores
- Bank online-banking lockouts
- Enterprise directory services

<a id="brute"></a>
## Brute force, work factor, GPUs & Moore’s Law

Brute force tries all keys. Work factor is the time or resources needed to defeat protection. GPUs and Moore’s Law keep eroding it, so “adequate” encryption must be reviewed.

**Flow:** Define key space → Guess rate → Time to search → Hardware improves → Re-evaluate strength

### Working principle
1. **Define key space**: Key space is 2^bits (DES 56 bits was eventually exhausted).
2. **Guess rate**: Rate: a CPU may take 48 hours on an 8-character mixed password; a modern GPU under 10 minutes thanks to many arithmetic logic units.
3. **Time to search**: Expected time is about half the key space divided by the rate.
4. **Hardware improves**: Moore’s Law: compute doubles roughly every 18 months (possibly slowing), so strength adequate today may not be later.
5. **Re-evaluate strength**: Adequate encryption is one whose work factor exceeds what the attacker wants to invest. Reassess length, complexity and multifactor authentication.

### Pros
- Gives a way to compare strength
- Longer keys scale defense exponentially

### Cons
- Only a rough estimate
- Hardware and techniques improve over time

### Where it is deployed
- Choosing AES-128 vs 256
- Password policy design
- Crypto-agility planning in banks and defense
- Retiring DES, SHA-1, MD5

<a id="birthday"></a>
## Birthday attack & hash collisions

It is far easier to find any two messages with the same digest than to match one specific digest. Cost is about 2^(n/2) instead of 2^n, so digests must be twice as long as the desired work factor.

**Flow:** Generate messages → Hash each → Store digests → Collision found → Forged equal-hash message

### Working principle
1. **Generate messages**: Attacker prepares many message variants.
2. **Hash each**: Each is hashed to an n-bit digest.
3. **Store digests**: Digests are stored and compared with all earlier ones.
4. **Collision found**: After about 2^(n/2) tries two different messages share a digest.
5. **Forged equal-hash message**: The forged message passes integrity checks. Countermeasure: digest twice the work factor (SHA-1’s 160 bits gives only 2^80).

### Pros
- Explains why 128-bit hashes are weak
- Guides digest-length choice

### Cons
- Real collisions broke MD5 and SHA-1
- Needs attacker-controlled messages

### Where it is deployed
- Forged certificates (MD5 attack)
- Document signing safety
- Hash selection in standards (SHA-256/3)
- Blockchain hash design

<a id="freq"></a>
## Frequency analysis

In a substitution cipher each letter maps to another, but language statistics survive. In English E, T, A, O, I, N are most common, so the commonest cipher letters are likely those.

**Flow:** Ciphertext → Count letters → Rank by frequency → Map to ETAOIN → Read the text

### Working principle
1. **Ciphertext**: Collect the ciphertext.
2. **Count letters**: Count each letter.
3. **Rank by frequency**: Sort from most to least common.
4. **Map to ETAOIN**: Assign the most common cipher letters to E, T, A, O, I, N… and refine with word shapes.
5. **Read the text**: The plaintext emerges. Works with other attacks; modern ciphers hide statistics.

### Pros
- Cheap to run, teaches cryptanalysis

### Cons
- Needs enough text
- Useless against modern block and stream ciphers

### Where it is deployed
- Breaking classical ciphers (historic wartime codebreaking)
- Puzzle and forensic analysis
- Teaching
- Detecting weak custom ciphers in audits

<a id="replay"></a>
## Replay attack

The attacker captures a valid message and resends it. Without sequence numbers, nonces or timestamps the host processes duplicates.

**Flow:** Valid transaction → Attacker captures → Attacker resends → Receiver checks → Reject or process twice

### Working principle
1. **Valid transaction**: A legitimate payment is sent.
2. **Attacker captures**: The attacker records the packet; it is authentic, so no key is needed.
3. **Attacker resends**: The attacker sends the same packet again.
4. **Receiver checks**: The receiver looks for a sequence verification code or fresh number.
5. **Reject or process twice**: With no check, the duplicate is processed (double charge). With a check, it is rejected. Wi-Fi CCMP’s 48-bit packet number does this.

### Pros
- Easy to defend with counters/nonces

### Cons
- Needs state at the receiver
- Clock sync for timestamps

### Where it is deployed
- Payment protocols
- Wi-Fi WPA2/3
- Car key-fob rolling codes
- Military command messages

<a id="impl"></a>
## Implementation attacks: side-channel, fault, probing, reverse engineering

The math can be sound while the product leaks. Implementation attacks measure timing and power, force errors, probe circuits, reverse engineer products or recover temporary files.

**Flow:** Target device → Observe / disturb → Collect leakage → Derive secret → Hardening

### Working principle
1. **Target device**: Attacker obtains the device, software or access to the workstation.
2. **Observe / disturb**: Side-channel analysis passively watches power, emanation, timing; fault analysis forces errors; probing watches nearby circuitry or adds hardware.
3. **Collect leakage**: Results are compared with known-good output; measurements correlate with key bits.
4. **Derive secret**: Reverse engineering found Netscape SSL’s random number generator too predictable, exposing IVs and nonces; undeleted temporary files may hold plaintext.
5. **Hardening**: Defenses: constant-time code, shielding, tamper-resistant modules, strong RNGs, wiping temporary files.

### Pros
- Awareness drives secure hardware design

### Cons
- Common because they ignore the algorithm
- Hard to see in software testing

### Where it is deployed
- Smart-card and HSM certification
- Payment terminals
- Military crypto modules (tamper resistance)
- Secure boot hardware

<a id="social"></a>
## Social engineering: RSA SecurID breach (2011)

Cryptosystems rely on people. Deception, coercion or bribery bypass the math; the 2011 RSA breach started with phishing and cost about US$66 million.

**Flow:** Phishing emails → Employee opens Excel file → Zero-day Flash exploit → Backdoor installed → Tokens compromised, replaced

### Working principle
1. **Phishing emails**: Two phishing emails target RSA employees.
2. **Employee opens Excel file**: One opens an attached Microsoft Excel spreadsheet.
3. **Zero-day Flash exploit**: The spreadsheet exploits a zero-day Adobe Flash flaw.
4. **Backdoor installed**: A backdoor gives the attacker access to the network.
5. **Tokens compromised, replaced**: Two-factor SecurID security was undermined, affecting several US defense contractors; RSA replaced all tokens (~US$66 million). Defense: constant awareness, training and education.

### Pros
- Training is cheap compared with breaches

### Cons
- Humans are the greatest vulnerability
- Advanced persistent threats are patient

### Where it is deployed
- Security awareness programs
- Phishing simulations
- Defense contractor supply-chain security
- Incident response planning

<a id="quantum"></a>
## Quantum cryptanalysis & post-quantum cryptography

Quantum cryptography uses physics to create and share keys. Quantum computing could break RSA and ECC (Shor’s algorithm) and weaken symmetric keys (Grover); post-quantum algorithms are being prepared.

**Flow:** Today: classical limits → Micius entanglement → Quantum computer? → Public keys at risk → Post-quantum migration

### Working principle
1. **Today: classical limits**: RSA-250 (829 bits) was factored in 2019; larger keys remain impractical to attack classically.
2. **Micius entanglement**: Micius satellite (China, 2017) demonstrated entanglement over a space-to-ground link, a building block for key distribution; quantum cryptography is not yet used to encrypt or store data.
3. **Quantum computer?**: A practical quantum computer would be orders of magnitude more powerful than supercomputer arrays.
4. **Public keys at risk**: Then most current public-key systems would not withstand concerted attack; symmetric keys lose roughly half their bits.
5. **Post-quantum migration**: Research on post-quantum cryptography (governments, military and the Open Quantum Safe project) prepares replacements; NIST has standardized lattice-based schemes.

### Pros
- Key distribution tamper evidence
- Post-quantum algorithms run on classical machines

### Cons
- Large quantum computers do not exist yet
- Migration is slow and costly

### Where it is deployed
- Government and defense planning (store-now-decrypt-later)
- Bank crypto-agility programs
- Quantum-secured links (Micius, fibre networks)
- Open Quantum Safe prototypes

<a id="hygiene"></a>
## Cryptographic hygiene

Practices that keep cryptosystems strong. Strength is hard to measure: bugs creep into complex systems like PKI, and luck can beat skill, so ongoing care matters.

**Flow:** Inventory → Update suites → Monitor threats → Manage keys → Use vetted libraries

### Working principle
1. **Inventory**: Inventory session keys, certificates and related materials; validate them.
2. **Update suites**: Keep algorithm suites at the latest versions.
3. **Monitor threats**: Watch threat intelligence for early signs of trouble.
4. **Manage keys**: Invest in key management and storage, especially for backup and archive keys.
5. **Use vetted libraries**: Use validated libraries for authentication; forbid inventing your own cryptography.

### Pros
- Cheap relative to a breach
- Keeps pace with new attacks

### Cons
- Ongoing effort
- Strength never certain: work factor is a rough estimate

### Where it is deployed
- Banks and payment processors (PCI DSS audits)
- Defense accreditation
- Hospitals
- Cloud providers
