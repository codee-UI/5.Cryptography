# Applied Cryptography: Secure Protocols & Key Management

Companion to the interactive simulator (`crypto-simulator.html`). Each topic lists the working principle step by step, pros, cons and real deployments.

## SSL/TLS protocol stack
```
Application : HTTP | FTP | Telnet | Other
--------------------------------------------
Handshake layer : Handshake | Change Cipher Spec | Alert
Record layer    : fragment -> compress -> MAC -> encrypt
--------------------------------------------
Transport   : TCP/IP
```

## 1 · Secure protocols & CIA
Secure protocols plus encryption give Confidentiality, Integrity and Authenticity for data in transit and at rest. Online banking is the classic use case.

**Working principle (steps)**
1. **TLS + certificate** (Customer → Bank server): Browser opens a TLS session. The bank certificate proves identity (Authenticity) and SSL/TLS stops eavesdropping and impersonation.
2. **AES(card, PIN)** (Customer → Bank server): Sensitive data is encrypted with a symmetric key (AES): only authorised parties can read it (Confidentiality).
3. **altered packet** (Attacker → Bank server): An attacker modifies data in transit. The hash/MAC no longer matches, so the bank rejects it (Integrity).
4. **AES at rest** (Bank server → Database): Server stores records encrypted with AES; keys live in an HSM/KMS. 3DES, RSA/ECC are older or special-purpose options.
5. **SFTP / HTTPS** (Bank server → Customer): Statements travel by SFTP/SCP, web pages by HTTPS, PII by TLS (GDPR, CCPA). Passwords are hashed (SHA), never MD5.

**Pros**
- Protects data in transit and at rest
- Meets regulations (PCI DSS, GDPR, CCPA)
- Builds customer trust

**Cons**
- Complexity: protocols layered on protocols
- Key management burden
- Performance overhead

**Applications (commercial, defence, other)**
- Online banking, card payments, e-commerce
- Healthcare records (HIPAA)
- Government e-services, cloud storage

## 2 · SSL / TLS
TLS sits between the application layer and TCP/IP. Handshake layer (Handshake, Change Cipher Spec, Alert) negotiates; Record layer fragments, compresses (legacy), adds a MAC and encrypts. SSL is deprecated and banned by PCI DSS.

**Working principle (steps)**
1. **ClientHello** (Client → Server): Client sends supported TLS versions, cipher suites and a random number.
2. **ServerHello + Cert** (Server → Client): Server picks version and cipher suite and sends its X.509v3 certificate (public key, serial, validity, CA signature).
3. **verify cert** (Client → CA / Root): Client checks the CA signature chain, validity period and revocation status.
4. **trusted ✔** (CA / Root → Client): Chain leads to a trusted root: the server identity is authenticated.
5. **pre-master secret** (Client → Server): Client sends a secret encrypted with the server public key (or uses Diffie-Hellman). Asymmetric crypto is used only here.
6. **derive keys** (Client → Client): Both sides compute the master secret, then symmetric session keys and MAC keys from the exchanged data.
7. **ChangeCipherSpec + Finished** (Client → Server): Client announces: from now on everything is protected with the negotiated keys.
8. **ChangeCipherSpec + Finished** (Server → Client): Server confirms. Handshake complete.
9. **Record: AES + HMAC** (Client → Server): Record protocol splits data into fragments, adds a MAC, encrypts with fast symmetric AES and sends over TCP.
10. **Alert: close_notify** (Server → Client): Alert sub-protocol signals errors or an orderly close.

**Pros**
- Transparent to many application protocols
- Strong hybrid crypto: speed plus safe key exchange
- Server (and optionally client) authentication
- Mature, widely supported

**Cons**
- Needs PKI/CA trust and certificate upkeep
- Handshake adds latency and CPU cost
- Old SSL/early TLS are vulnerable (POODLE, BEAST)
- Misconfiguration risk

**Applications (commercial, defence, other)**
- HTTPS web, online banking, e-commerce (PCI DSS)
- Email transport (SMTPS, IMAPS), VoIP signalling
- Military/government portals
- OpenVPN, mobile app APIs

## 3 · Hybrid crypto, hash & HMAC
Asymmetric crypto safely shares a key; symmetric crypto encrypts the bulk data. Hashes give integrity; HMAC adds a shared secret for proof of origin.

**Working principle (steps)**
1. **digest = H(msg)** (Sender → Sender): A hash algorithm (agreed in handshake) creates a fixed-size digest of the entire message.
2. **HMAC = H(msg + secret)** (Sender → Sender): A second shared secret is mixed into the hash, giving integrity AND basic proof of origin.
3. **session key (RSA/DH)** (Sender → Receiver): Asymmetric encryption or Diffie-Hellman delivers the session key over an insecure channel.
4. **AES(msg) + HMAC** (Sender → Receiver): The message is encrypted with the fast symmetric session key and sent with the HMAC.
5. **recompute and compare** (Receiver → Receiver): Receiver recomputes the HMAC. Match = untampered and from someone holding the secret.
6. **forged message** (Attacker → Receiver): Attacker has no secret key, so the HMAC does not match: message discarded.

**Pros**
- Speed of symmetric + key distribution of asymmetric
- Detects tampering
- HMAC proves origin

**Cons**
- Both sides must protect the shared secret
- Weak hashes (MD5, SHA-1) are broken
- Does not hide message length/metadata

**Applications (commercial, defence, other)**
- TLS, IPsec, SSH sessions
- API request signing (JWT-HS256, AWS SigV4)
- Secure software updates, banking messaging

## 4 · PKI & certificates
PKI publishes public keys and binds them to identities through certificates signed by a Certificate Authority, organised in a hierarchy of trust (root CA at the top).

**Working principle (steps)**
1. **generate key pair** (Organisation → Organisation): Owner makes a public/private pair and keeps the private key secret.
2. **CSR + identity proof** (Organisation → RA): Certificate request with the public key; the Registration Authority checks the requester identity (calls, documents).
3. **identity confirmed** (RA → CA): RA vouches for the requester to the CA.
4. **signed X.509 cert** (CA → Organisation): CA issues a certificate binding identity to public key: serial no., validity period, issuer, digital signature.
5. **present certificate** (Organisation → Browser): Website sends its certificate when the browser connects.
6. **verify chain** (Browser → Root CA): Browser follows intermediate CA to a trusted root (hierarchy of trust); cross-certification links separate roots.
7. **CRL / OCSP** (CA → Browser): Revocation status is checked so stolen or expired certificates are rejected.
8. **🔒 trusted** (Browser → Browser): Valid dates + good signature + not revoked = padlock shown.

**Pros**
- Scales to billions of users
- Strong, standardised identity binding
- Enables TLS, signing, email encryption

**Cons**
- Single point of failure if a CA is compromised
- Cost and admin of certificates
- Revocation checking is imperfect
- Does not suit small orgs (NIST SP 1800-16 gap)

**Applications (commercial, defence, other)**
- HTTPS websites, code signing
- Government eID and e-passports
- Military PKI (CAC cards), banking, enterprise Wi-Fi/VPN

## 5 · Web of trust (PGP)
Decentralised alternative to CAs, proposed by Phil Zimmermann (1992). Peers vouch for each other public keys.

**Working principle (steps)**
1. **Alex trusts Sam** (Alex → Sam): Alex already knows and trusts Sam key.
2. **Sam signs Zach key** (Sam → Zach): Sam has verified Zach in person and signed his public key.
3. **Sam vouches** (Sam → Alex): Sam tells Alex: this really is Zach key. Trust is transitive through the web.
4. **encrypt with Zach pub** (Alex → Zach): Only Zach private key can decrypt: confidentiality.
5. **spoofed key** (Fake key → Alex): A fake Zach key has no trusted signatures, so Alex rejects it.

**Pros**
- No central authority or fees
- Fault-tolerant; users can link several webs

**Cons**
- Hard to scale; needs user effort
- Trust decisions are subjective
- Revocation is hard

**Applications (commercial, defence, other)**
- PGP / GnuPG / OpenPGP email
- Open-source package signing (Linux)
- Journalists, activists, developer communities

## 6 · IPsec
Suite securing IP with authentication and encryption (mandatory in IPv6). Components: IKE/ISAKMP, SA, AH, ESP; modes: tunnel (default) and transport.

**Working principle (steps)**
1. **IKE Phase 1** (Gateway 1 → Gateway 2): Peers authenticate with shared secret, certificates or nonce-based revised public-key mode, creating a temporary SA and secure channel.
2. **IKE Phase 2** (Gateway 1 → Gateway 2): Inside that tunnel they negotiate IPsec SAs. An SA is one-way, so two SAs are needed for two-way traffic.
3. **plain IP packet** (Host A → Gateway 1): Host sends ordinary traffic to its gateway.
4. **encapsulate (tunnel)** (Gateway 1 → Gateway 1): Tunnel mode: entire packet plus header becomes the payload of a new IP packet.
5. **ESP: SPI+seq | enc | auth** (Gateway 1 → Gateway 2): ESP header (SA id, sequence no.), encrypted payload (symmetric, IV), trailer/padding, integrity value.
6. **AH: hash + seq** (Gateway 1 → Gateway 2): AH variant gives integrity and anti-replay only (no encryption). Sequence numbers thwart replay.
7. **NAT-T UDP 4500** (Gateway 1 → Gateway 2): NAT changes IP headers (seen as attack), so IPsec is wrapped in UDP 4500.
8. **decrypt + verify** (Gateway 2 → Host B): Gateway verifies, decrypts and delivers. Transport mode (Host A to B directly) protects only the payload; HAIPE devices harden this for military use.

**Pros**
- Works at IP layer: protects all applications
- Strong encryption and anti-replay
- Standard, interoperable (IKE/PKI)
- Hardware (HAIPE) option

**Cons**
- Complex configuration
- NAT issues (need NAT-T)
- Authenticates hosts, not users, unless L2TP/proprietary
- Overhead added to packets

**Applications (commercial, defence, other)**
- Site-to-site VPNs between firewalls
- Military and government links (HAIPE)
- Rail, air, emergency services CCTV/telemetry
- Remote workers (L2TP/IPsec)

## 7 · VPN protocols
A VPN is a point-to-point connection; security depends on the protocol chosen: PPTP (weak), L2TP (needs IPsec) and OpenVPN (SSL/TLS).

**Working principle (steps)**
1. **PPTP: TCP 1723 + MS-CHAPv2** (Remote user → VPN gateway / LNS): PPTP authenticates the user, then builds a PPP session tunnelled through GRE. Key derived from the password: weak.
2. **L2TP: PPP dial-in** (Remote user → ISP / LAC): User reaches the ISP L2TP Access Concentrator (LAC) over PPP.
3. **L2TP UDP 1701 → LNS** (ISP / LAC → VPN gateway / LNS): LAC encapsulates PPP into L2TP and forwards to the LNS, which authenticates the user. L2TP has no encryption.
4. **add IPsec ESP** (ISP / LAC → VPN gateway / LNS): L2TP/IPsec: tunnel-mode IPsec supplies confidentiality.
5. **OpenVPN: TLS + certs** (Remote user → VPN gateway / LNS): OpenVPN authenticates with certificates, pre-shared keys or user/password and uses OpenSSL/TLS.
6. **access intranet** (VPN gateway / LNS → Corp. network): After authentication the user gets office-like access to resources.

**Pros**
- Cheaper than leased lines
- Remote and branch access
- OpenVPN: open source, flexible, firewall-friendly

**Cons**
- PPTP broken: do not use
- L2TP alone is not encrypted
- Password-only auth is weak (prefer 2FA)
- Misconfiguration voids security

**Applications (commercial, defence, other)**
- Corporate remote work
- Gateway-to-gateway links to partners
- Defence contractors and field units
- Privacy/commercial VPN services

## 8 · Steganography & null cipher
Cryptography protects the contents of a message; steganography hides its existence. A null cipher hides it inside ordinary plaintext. Try the live demos below the stage.

**Working principle (steps)**
1. **secret message** (Sender → Sender): Optionally encrypt first, then hide: doubly protected.
2. **embed in LSBs** (Sender → Cover file): Least significant bit of each pixel/audio byte is replaced by a secret bit: change is invisible.
3. **looks like a normal image** (Cover file → Receiver): File travels openly (also: covert channels, hidden web text, invisible ink, microdots).
4. **nothing suspicious** (Warden → Cover file): Observer sees only an ordinary picture.
5. **extract LSBs** (Receiver → Receiver): Receiver with the right tool reads the hidden bits.
6. **null cipher** (Sender → Receiver): Words carry the message: take the first letter of each word of an innocent sentence.

**Pros**
- Hides that communication exists
- Digital watermarking proves ownership
- Combines with encryption

**Cons**
- Low capacity; fragile to compression
- Steganalysis can detect it
- Security by obscurity if used alone
- Abused for malware C2 and exfiltration

**Applications (commercial, defence, other)**
- Copyright watermarking, document tracing
- Intelligence/military covert messages (e.g. 1898 null cipher)
- Censorship circumvention
- Printer tracking dots, forensics

## 9 · Key management lifecycle
Most cryptosystems fail through key management, not algorithms. Kerckhoffs/Shannon: security rests on the key, not on secrecy of the algorithm.

**Working principle (steps)**
1. **generate (random)** (RNG / generator → KMS / HSM): Use hardware RNG or approved PRNG (NIST, ISO 18031). Manual keys cluster and are guessable. Mind key space size and distribution.
2. **wrap with KEK** (KMS / HSM → KMS / HSM): Key-encrypting key wraps session keys; each record signed/MACed; keys stored in HSM, smart card or split.
3. **distribute** (KMS / HSM → Users): Diffie-Hellman, certificates or courier, protected against MITM. XKMS: X-KISS locates/validates keys, X-KRSS registers/recovers.
4. **use within cryptoperiod** (Users → Users): Keys expire (see table): short periods limit exposure, but too-frequent manual rekeying invites errors.
5. **backup / archive** (KMS / HSM → Archive): Back up root keys, allow recovery, keep key history for old backups, audits and litigation.
6. **revoke / destroy** (Archive → Destroy): Retire expired or compromised keys; keep verify-only copies to validate old signatures; wipe securely.

**Pros**
- Central control, audit, rotation
- Limits damage from compromise
- Meets compliance

**Cons**
- Single point of failure (vault/HSM)
- Human error, cost, complexity
- Maturity path: unmanaged → password vault → enterprise KMS

**Applications (commercial, defence, other)**
- Cloud KMS (AWS, Azure, Google)
- HSMs in banks and payment networks
- Military key loading devices
- Enterprise PKI, database encryption

## 10 · Limitations & vulnerabilities
Layering protocols on protocols raises complexity. Limits: computation, key management, human factors. Vulnerabilities: cryptanalysis, implementation errors, protocol flaws.

**Working principle (steps)**
1. **cryptanalytic attack** (Cryptanalyst → Crypto system): Brute force, frequency, differential, linear or side-channel analysis; works on short keys or weak algorithms.
2. **human factors** (Humans → Crypto system): Weak or reused passwords, shared keys, phishing, coercion.
3. **implementation error** (Developers → Crypto system): Bugs, poor testing or backdoors in code or integration.
4. **protocol flaws** (Protocol attacker → Crypto system): Replay, man-in-the-middle and denial-of-service via design flaws.
5. **computational cost** (Crypto system → Crypto system): Bigger keys = slower, more memory and power.
6. **key management** (Crypto system → Crypto system): Loss, theft, rotation and revocation mistakes (even Enigma fell to discarded keys).

**Pros**
- Knowing the risks drives better design

**Cons**
- Cryptography is only as strong as its weakest link
- No algorithm is secure forever

**Applications (commercial, defence, other)**
- Security audits, threat modelling
- Penetration testing, compliance reviews
- Post-quantum cryptography planning
